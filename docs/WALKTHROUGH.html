What it is

SDLC Pipeline

The pipeline reads a ticket and its tech spec, plans the change across the repos it touches, writes the code, reviews it, writes the deployment note and hands QA a test guide. You make the decisions that matter: which ticket, which plan, which findings to fix, when to merge, and whether QA passes.

What goes in

  • A Jira ticket with numbered acceptance criteria
  • A link to the tech spec in Google Docs, pasted in the terminal
  • The repos it touches, ticked in the terminal

What comes out

  • One merge request per repo, linked and in merge order, opened only after the review has approved
  • A review where every criterion was checked with evidence (optionally also proven by real calls on this machine)
  • One review summary comment on each merge request
  • A deployment note and QA test notes with ready cURLs

What people keep

  • Which tickets the AI takes
  • Approving the plan, and which review findings to fix
  • Merging in GitLab, infrastructure changes and the QA verdict

Where you decide

By default people decide at four points; everything between runs by itself, in the terminal (pipeline cli). More steps can be made manual in the config.

You pick the ticket→ Plan→ You approve the plan→ Code · check · review · fix · merge requests · deployment note→ You merge→ QA passes or fails

Jira: statuses and a user for the pipeline

Jira holds the tickets and the audit trail. The repos and the tech spec are no longer read from Jira fields: whoever starts a ticket gives them in the terminal (the next chapters show how).

What to set up

WhatDetails
Seven statusesTo Do, In Dev, Blocked, RFT, Testing, QA Failed, QA Passed. The pipeline moves tickets between them, so allow those transitions. Other names? Set them under jira.statuses in the config.

Setup 3 of 4

Files each product repo needs

Every repo carries its own standards and its own review checklist. This is how the agents learn how this team writes code, instead of writing generic code. They are committed to the repo’s default branch.

FileRead byWhat is in it
CLAUDE.mdPlanner, Coder and Reviewer on Claude (loaded automatically)The repo’s standards, with real file paths: what the repo owns and its folder layout; how to add an endpoint end to end; naming, response and error shapes; gateway: validation rules, auth, how to call a service (client, base URL variable, timeout, error mapping table), how to mock services in tests; service: internal endpoint conventions and auth, where business logic lives, database access, migration rules (tool, naming, up and down, never edit an old migration); env vars go into .env.example; logging and errors; how to test; commands; Do and Don’t (no unrelated changes, no new dependencies unlisted, no CI changes); the commit format feat(DEMO-12): …; and the rule: when you get .agent/contract.json, implement or call exactly those endpoints, and if you cannot, stop and report a deviation. Two or three “golden” files show the team’s best style. Kept under about 300 lines.
AGENTS.mdThe same agents when a slot runs on CodexAn identical copy of CLAUDE.md, with a note at the top: “Keep CLAUDE.md and AGENTS.md identical”. Codex reads this name.
REVIEW.mdReviewerThe checklist the reviewer walks through: conformance to the spec and task, correctness and edge cases, security (validation, authorisation, secrets, parameterised queries, internal endpoints not public), gateway: validation matches the contract, timeouts, complete error mapping, no business logic that belongs in a service; service: reversible migrations, transactions, indexes; performance; tests; the repo’s standards; DevOps impact declared. It ends with the severity definitions (blocker, major, minor, nit), one example each.
DEPLOYMENT_TEMPLATE.mdDeployment agentThis repo’s deployment sections (environment variables, database migrations, infrastructure, rollback), each with an explicit “None” form and this repo’s real rollback commands. The pipeline merges every repo’s notes into one note per ticket.
.env.exampleCoder, and the pipelineEvery variable the code reads, with a comment. A coder that adds a variable must add it here; the pipeline compares the code with this file to find variables nobody declared.
.gitignoreGitContains .agent/, the scratch folder where agents get their inputs and leave their results. It is never committed.

The repo’s own lint and test scripts must work, because the pipeline re-runs them itself (the commands are in the config).

Project rules live here, not in the pipeline. A rule such as “validation lives in the controller, the service only does the database work” or “never edit the authentication middleware” goes in that repo’s own CLAUDE.md (and its REVIEW.md), so every coder and reviewer sees it. Files that must never change can also be listed in repos[].shared_paths in the config; the pipeline blocks and undoes edits to them.

How the files get tested

Each repo was hand-run once before being used: a fresh Claude Code session got a ticket, the spec and a hand-written contract, and the result was compared with the standards. Every miss was fixed in CLAUDE.md or REVIEW.md. That step is the most valuable one: specific beats general, and real file paths beat advice.

What the pipeline creates on the machine

Everything lives under $PIPELINE_HOME. Nothing is written into your own clones.

~/.ai-pipeline/
├─ pipeline.db              state: where every ticket is (checkpoints) + history (events, runs, commands)
├─ repos/<repo>/            base clones, one per repo
├─ specs/<docId>.md         the cached tech specs
├─ workspaces/DEMO-12/      one folder per ticket
│  ├─ .agent/               the ticket's one scratch folder: ticket.md, spec.md, spec_excerpt.md, repo_map.md,
│  │                        plan.json, contract.json, result.json, commits.json, review.json …
│  ├─ nodejs-ws1closio/             a git worktree of the gateway, on its own branch ai/DEMO-12-…
│  └─ nodejs-ws2targetsalesincentive/   a git worktree of the service, same layout
├─ runs/DEMO-12/            the full transcript of every agent run (secrets masked)
├─ secrets/                 the Google login files
└─ logs/pipeline.log
  • A worktree is a separate working copy of a repo on its own branch, so several tickets and repos never disturb each other.
  • The .agent/ folder is how agents talk. An agent never talks to another agent directly: it reads files left by the step before, writes its own result file, the pipeline checks it, and the next step picks it up.
How it is connected

Two layers: a thin one that talks, a heavy one that works

People talk to the orchestrator through one terminal (pipeline cli); it is a Python program running a LangGraph workflow. It never writes product code. When code, a review or a document is needed, it hands the job to an agent: Claude Code or Codex running inside the repo's own working copy. Click any box.

The pipeline itself, plain code with no model, does the reading of the ticket, the environment check, verifying, running the live tests, opening the merge requests and every write to Jira and GitLab.

1. Start and read the ticket

pipeline, no model

You type

implement DEMO-12

The terminal asks for the tech spec link (it must be a Google Doc the pipeline can read, otherwise Cannot implement DEMO-12: <reason> and nothing starts) and shows the config’s repositories as a numbered list to pick from. Add testing=true to include the live tests, or give --spec and --repos to skip the questions.

Gets

  • The Jira ticket: summary, description, acceptance criteria
  • Your answers (spec link, repos), kept so a retry or restart reuses them
  • The tech spec from Google Docs

Does

  1. Checks the ticket has criteria and that the repos are known. If something is missing it says so and stops. It never guesses repos.
  2. Fetches the whole spec once and caches it in specs/<docId>.md (a changed spec is picked up on the next plan).
  3. Moves Jira to In Dev and starts the delivery summary comment.

Leaves

  • The cached spec, and the first saved checkpoint in pipeline.db

read onlyCoder pool

Turns one ticket into one task per repo and one interface contract: the exact REST endpoints between the gateway and the services. The contract is what makes the pieces fit. Every acceptance criterion must be assigned to a task.

The pipeline prepares (no model involved)

File or folderWhat it is
worktreesFor each repo: fetch the base clone and create a working copy on branch ai/DEMO-12-… from the latest develop
.agent/ticket.mdThe ticket: summary, repos, the criteria the pipeline found, the full description
.agent/spec.mdThe whole tech spec (often thousands of lines)
.agent/spec_excerpt.mdAbout 40 KB out of 400: the sections that specify this ticket’s endpoint, the definitions of its tables (found by CREATE TABLE, with their same-prefix siblings), what those sections refer to, matching error sections, plus the spec’s table of contents
.agent/repo_map.mdPer repo: folders, and the files nearest to the ticket with their functions and routes
.agent/repos.jsonName, role and path of each repo in this ticket

The prompt already contains the planner’s instructions, the ticket, the excerpt, the repo map, each repo’s CLAUDE.md and the first nearby source files, so it reads only a few more itself.

It writes: .agent/plan.json

  • Brief: every acceptance criterion as AC1…ACn in one format, and the shared preconditions
  • Contract: each internal endpoint (method, path, auth, request and response shape, errors) and each public endpoint (validation, which internal calls it makes, error mapping), with notes citing the spec sections
  • Tasks per repo: a summary, up to six steps, every file it adds or edits, which criteria and endpoints it covers
  • The flow through the repos, risks, and open questions

The pipeline then checks it

  • Every criterion is in some task; every new endpoint has a repo that implements it; ids are consistent
  • No invented tables: a table that sits next to the spec’s tables but is not defined by the spec rejects the plan
  • A problem goes back to the same session to fix. A second failure stops for help.

5. Coder agent

one session for all reposCoder-A, B, C

Implements the whole ticket in one session: it goes through the repos in plan order (services first, then the gateway), in each repo’s worktree. The prompt holds the plan, the compact interface, the ticket, the spec sections, each repo’s standards and the closest existing files and tests, so it does not hunt for them. The same conversation later fixes review findings, so it remembers what it wrote.

  B --> C["Per repo: writes code and tests, runs lint and the tests it touched"]

Writes

FileWhat it is
the code and testsInside the ticket’s worktrees only. Never CI files, never .env (except .env.example), never a protected file.
.agent/commits.jsonA commit plan: for each repo [{message, files}], one entry per module or mini feature with its tests
.agent/result.jsonOne result per repo: status, summary, files changed, test results, new env vars, migrations, new dependencies, API changes, contract deviations, open questions

Rules

  • It never commits or pushes. The pipeline makes one small commit per plan entry (type(DEMO-12): what), then one for anything left over.
  • It runs each check once, at most 3 self-fix attempts, then hands in honestly. The pipeline runs every check itself afterwards.
  • A repo’s own rules apply: what is in its CLAUDE.md (for example “validation lives in the controller”, “never edit the authentication middleware”) and the files in shared_paths are enforced; an edit to a protected file is undone.
  • A coder that cannot follow the contract stops and reports instead of deviating silently: the Planner replans once, a second deviation goes to a person.
  • If a result file does not validate, the session is asked to correct it in place.

6. Check (verify)

pipeline, no model

The pipeline re-runs every check itself. An agent saying “tests pass” counts for nothing. One repo at a time, services first, then the gateway.

flowchart LR
  A["Install if the lock file changed"] --> B["Lint the changed files"]
  B --> C["Run the tests and extra checks: coverage, circular imports"]
  C --> D["Forbidden files and secret scan"]
  D --> F{"All ok?"}
  F -- "yes" --> G["Next step"]
  F -- "no" --> H["verify_failures.md back to the same coder: up to 4 attempts"]
  • Forbidden: CI files, .env files, deployment notes in the repo. A secret scan runs on the diff.
  • Repo scripts run without the pipeline’s credentials. A flaky test is re-run once before it counts as a failure.
  • A machine problem (Redis down, disk full, VPN off) stops at once and says so. It is never blamed on the coder.

Writes: .agent/acceptance_plan.json

  • For every criterion in each repo, one or more cases: rows to seed, HTTP calls, expected status and error code, read-only database checks
  • A blocked list for what cannot be tested here (another partner’s data, forcing a server failure), each with the reason

The pipeline then

  • Checks every case against its rules, runs it, and writes acceptance.json with every result and its evidence
  • Deletes each case’s own rows right after it, by primary key, children first
  • Gives the reviewer acceptance_summary.md: the criteria already proven, which it does not check again

8. Reviewer agent and contract check

read onlyReviewer-A, B

One review session reads every repo and runs the cross-repo contract check in the same conversation. By default (REVIEW_MODE=local) this happens on this machine, before any merge request exists: the Reviewer reads each repo’s branch against its default branch. It did not write the code and does not trust anyone’s description: it checks the code itself.

The Reviewer gets

FileWhat it is
The diffThe branch against its default branch, from git (the merge request’s diff once it exists). Review this change, not the whole repo.
The planEach repo’s task with the criteria ids, and the contract, in the prompt
verify.jsonThe pipeline’s own check results

ticket.md, spec_excerpt.mdThe ticket and the spec sections for this repo
acceptance_summary.mdCriteria already proven by real calls: “don’t verify these again”

It checks

  1. Every acceptance criterion: met with evidence (file and line, or the test that proves it), not met, unknown, or not applicable with a reason. A criterion that is not met becomes a finding by itself.
  2. The contract: exactly the contract’s endpoints, methods, shapes, headers and error codes.
  3. REVIEW.md, section by section.
  4. Code quality: reuse (an existing helper not used; the same logic in two places), efficiency (queries in loops, missing pagination, independent awaits in sequence), and the repo’s own best practices.

Writes: .agent/review.json (a result per repo, plus the contract)

  • A verdict (approve or changes requested) and a summary
  • Findings: id, severity (blocker, major, minor, nit), file, line, comment, suggestion
  • An answer per criterion, and, from round 2, an answer per earlier finding: fixed, still open, or withdrawn

The contract check

Reads all the diffs against the whole contract. For every internal endpoint it compares the service with the gateway: the same method and path, request validation that fits, every contract error mapped as error_mapping says, response shapes that match, and nothing outside the contract.

9. Fix loop

Coder, then the Reviewer again
flowchart LR
  A["Findings in scope: blockers and majors by default"] --> B["Coder: fixed, disputed or not applicable, per finding"]
  B --> C["Pipeline re-checks; the fixes are committed locally"]
  C --> E["Reviewer answers every earlier finding: fixed, still open, withdrawn"]
  E --> F{"Approved?"}
  F -- "yes" --> G["Merge requests open"]
  F -- "no, rounds left" --> A
  F -- "no progress twice, or 6 rounds" --> H["Stops for a person"]

The Fix coder gets

  • Only the findings in the chosen scope, plus your notes. It is the same session that wrote the code.
  • The original plan and contract, still authoritative. A finding that asks to break the contract is disputed, not followed.

You choose the scope

SayWhat gets fixed
(nothing: the default)Blockers and majors, automatically, without asking
fix DEMO-12 blockers  ·  major  ·  minor  ·  allBy severity
fix DEMO-12 #1 #2 #4 dismiss #3: reasonExactly those findings, with your notes to the coder; dismiss records one as rejected by you
accept DEMO-12Approve without fixing the rest. A recorded human override (asks to confirm).

The pipeline stops early and asks you when two rounds make no progress, a finding is disputed twice, or six rounds pass. Findings left open (minors) are written on each merge request, and you can still send them for fixing before the first merge.

10. Open the merge requests

pipelineafter the approval

In the default local review nothing has left this machine until now. Once the Reviewer approves, the pipeline publishes.

flowchart TD
  A["Reviewer approved"] --> B["Fetch, rebase each branch onto the latest default branch"]
  B --> C{"Conflicts?"}
  C -- "yes" --> D["Coder resolves them, checks run again"]
  C -- "no" --> E{"Did the rebase change the branch's own patch?"}
  D --> E
  E -- "yes" --> F["Back to the review"]
  E -- "no" --> G["Push with a lease"]
  G --> H["One merge request per repo, cross-linked, in merge order"]
  H --> I["One review summary comment and the Reviewer's approval on each"]
  • The branch is rebased onto the newest default branch before the push, so the merge request is current. It pushes with a lease pinned to what it saw, so a commit a person pushed in between is kept.
  • If the rebase leaves the branch’s own change identical (only the base moved), the approval carries to the new commit. If the change itself differs, the Reviewer looks again first.
  • The summary comment lists the review rounds, what was raised, fixed or dismissed, what stayed open or was accepted, and each acceptance criterion with its evidence. Nothing is cut.
  • The merge requests are opened by the Coder account and approved by the Reviewer account. The pipeline never pushes to a default branch and never merges.
  • REVIEW_MODE=gitlab keeps the earlier flow: merge requests first, then the review with findings as threads.

11. Deployment agent (DevOps)

read onlyDeploy-A

Writes one deployment note for the whole ticket after the review has passed and before anyone merges. DevOps does its part before the merges.

flowchart LR

  B --> C["Deployment agent writes the note"]
  C --> D["Order, env vars, migrations with undo, infrastructure"]
  D --> E["Attached to Jira, summarised in the terminal with a DevOps checklist"]

The pipeline detects (no model)

  • New and removed env vars, variables read by the code but missing from .env.example, migration files and seeders, infrastructure files, new dependencies, and notes such as a new service dependency or a worker. These are facts: the agent must describe every one.

The agent gets

  • devops_facts.json, deploy_repos.json, each repo’s diff, each repo’s DEPLOYMENT_TEMPLATE.md and migration files, the contract, the plan, the ticket and spec, and override.json if a person accepted open findings.

The note contains

  • Order: services first, then the gateway, then the frontend (a consumer goes after the providers it calls)
  • Per repo: environment variables (never real secrets), database migrations with the exact command, infrastructure, and rollback only for a repo with migrations (the undo command, and whether it loses data)

The note is never committed to a repo. It lives on Jira and in the terminal.

Merging

  • The pipeline never merges. It warns if a repo is merged before one it depends on. A commit pushed by a person after approval sends the ticket back to review.

QA notes agent

  • Gets ticket.md, contract.json, routes.json (the gateway’s changed routes with their full public paths and validators) and qa_context.json.
  • Writes qa_notes.json: for each public endpoint, three tests: a happy path, a validation error, a business edge case. Each is a ready cURL with {{QA_BASE_URL}} and {{QA_TOKEN}} placeholders (never real tokens), the expected result, and the criterion it covers.

QA bugs: one Jira ticket each

  • QA files every bug as its own ticket with the bug in the description, then moves the main ticket to QA Failed.
  • You type fix DEMO-12 and it asks for the bug ticket numbers, or fix DEMO-12 DEMO-13 DEMO-14 in one line. The pipeline reads each ticket’s summary and description, numbers the bugs (#1, #2 on the main ticket) and starts the round for all of them.
  • A QA round runs the same loop again, up to five rounds. The planner plans only the affected repos, and the review is automatic.
Proof before the merge requests

Live tests: the code is run for real before anyone reviews it

For a ticket started with testing=true, before the review the ticket’s apps start on this machine and a separate Tester agent’s cases call them over HTTP, against the team’s dev database. Each acceptance criterion is either proven by a real call or listed as unproven, with the reason. What a test creates is deleted again, and nothing else is ever touched.

The whole run

Click any box.

What a result means

  • passed: counts as proof, so the reviewer does not check it again
  • failed: goes back to the coder of that repo (and the services it calls)
  • blocked: cannot be proven here, and says why. It never stops the ticket; the reviewer reads the code instead
  • invalid: the case is wrong. The Tester fixes it once

What it never does

  • Touch rows it did not create: deletes are by primary key from its own ledger
  • Write through an agent: database checks are read only
  • Reach real outside services or a database that is not on the allowlist
  • Apply a migration. Only a person’s pipeline migrate does

Switches

  • acceptance.mode: off, advisory or required
  • Off by default for every ticket: implement DEMO-12 testing=true turns it on for one
  • pipeline env and pipeline acceptance run the check and the tests by hand; test DEMO-12 runs them again
Asking instead of guessing

When the requirement is unclear

Most questions are answered from the code and the spec before anyone is asked. Only a real gap or contradiction reaches a person, and the ticket simply waits for the answer. Click a box.

Why "approved" means something

Review and approval are backed by evidence

The Reviewer checks each merge request against that repo's own REVIEW.md, plus one cross-repo contract check. Findings are numbered and rated blocker, major, minor or nit. In the default local review they stay in the pipeline (the terminal, Jira and the final summary comment); in the GitLab review mode each becomes a thread on the diff. By default blockers and majors are fixed automatically and reviewed again, up to six rounds, and the loop stops early if two rounds make no progress.

What it will never do

Guardrails that do not depend on the AI behaving

Nothing leaves the machine before the review approves

In the default local review, branches are pushed and merge requests opened only after the Reviewer approves. Until then everything is in your own workspace.

Never merges, never pushes to a default branch

Humans merge in GitLab. Before every push the pipeline rebases its own branch onto the latest default branch and pushes with a lease, so a person's commit in between is kept.

Approval is tied to a commit

The approval names the reviewed commit. Any new commit on the merge request, from anyone, sends it back to review.

Least access

Reviewers, planners and doc agents can only write to a scratch .agent/ folder, checked by git. A coder only edits the ticket’s worktrees, never a protected file. Repo scripts and git run without the pipeline's credentials.

Secrets masked everywhere

Everything posted to the terminal, Jira and GitLab, and every transcript, is scrubbed. Agents never see production credentials. The summary agent gets no code unless you switch that on.

Safe to repeat

Every write carries a hidden marker, so a retry or restart never posts a comment twice or opens a second merge request.

Live tests touch only their own data

Allowlisted database hosts only, never prod. Deletes are by primary key from the run's own ledger. Agent-written checks are read only. Writes to real outside services are refused. The pipeline never applies a migration: a person does.

Stop, pause, override

stop halts a ticket. pause holds the whole pipeline. accept is a recorded human override of open findings, written to the merge request, the database and Jira.

Limits (safety nets, set well above a real ticket)

Review rounds6QA rounds5
Check attempts per repo4Replans3
Plan revisions10Live-test rounds sent back to the coder3

Hitting a limit never loses work: the ticket goes to Blocked with the reason, and a person decides. There is no cap on cost, agent runs per ticket or diff size. Each single agent run still has its own turn and time limit.

When things go wrong

Stop, resume, recover

Nothing lives only in a terminal window. Every step is saved, so work can stop at any point and carry on later, and every stop says why in plain words.

It stops safely

A failed step, a question, a limit or a person's stop moves the ticket to Blocked in Jira, with the reason in the terminal. Nothing half-done is pushed.

Your controls, any time

  • Try again (retry) runs the step that stopped
  • Guide adds your hint, then runs it again
  • Stop halts the ticket
  • Reset starts the ticket over
  • Pause holds the whole pipeline

Nothing is lost

The ticket's state is saved after every step. If the machine or the pipeline restarts, steps that were cut off carry on by themselves. Each ticket's working copies stay until it is done.

Where to look

The Jira delivery summary for decisions and status, status in the terminal, the report for runs and waiting time, and the full log of every agent run.
